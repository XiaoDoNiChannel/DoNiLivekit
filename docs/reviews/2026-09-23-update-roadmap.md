# DoNiChannel 分发与更新演进计划

日期：2026-09-23。范围：基于当前工作区的静态审查和官方技术文档提出方案；未执行发布、安装、升级或回滚演练。本文不表示以下能力已经实现。

## 决策建议

优先完善现有 Tauri 全量自动更新，实现“客户端下载准备好 → 用户选择时机 → 安装并重新启动”。随后提供绿色便携版，再根据连续版本的真实包体、下载耗时与失败率决定是否引入差分更新。

“客户端内更新”描述操作体验，“差分更新”描述传输方式，两者互不等同。全量自动更新也可以让用户不再打开网页、不再手动运行安装向导。发行方仍需为每版构建、签名和归档完整产物，差分方案也需要完整包作为首次安装与失败兜底。

这里将“纯净版”暂按免安装、解压运行、不捆绑无关软件、默认不自启动理解；若还要求离线运行或所有数据随目录移动，应另列明确承诺。免安装不代表不依赖 WebView2，也不代表自动把浏览器数据、日志和凭据都写在程序目录。

当前 JS 只分别去重检查和安装，检查结果仍可能覆盖下载/安装状态；拆分流程时统一更新状态机。安装阶段重新检查服务器还可能得到与用户先前看到不同的版本，应绑定用户确认的版本、产物标识与签名。

这些是代码层面的发现。当前用户仍手动下载安装的具体原因，需要结合其版本、更新地址、服务端清单和客户端日志定位，不能仅由代码断定。

## 分发产品

### 默认安装版

- 保留 NSIS，优先使用当前用户安装，减少管理员权限需求；现有机器级安装需要迁移测试。
- 无捆绑、自启动可选、数据目录明确，提供干净的安装及卸载体验。
- 更新后台准备、用户决定安装时机；初期允许简短安装进度窗口，不把完全无窗口作为首要验收条件。
- 区分 Tauri 更新产物签名与 Windows 程序代码签名，二者处理不同的信任问题。

### 绿色便携版

- 提供包含程序与必要运行文件的 ZIP，解压后运行，无须安装向导。
- 明确数据模式：默认用户目录，或显式开启的目录内数据模式；避免无意共享账号凭据。
- 便携版更新不能未经验证直接调用 NSIS 安装版更新。需要专用更新辅助程序，或经验证支持该场景的更新框架。
- 建议使用独立版本目录、稳定启动入口和独立用户数据目录；新版本完整写入并验证后再切换。
- 检查目录写权限、磁盘余量、文件锁、多实例；旧进程退出后才替换或切换，保留可恢复版本。
- 若第一版便携包尚不支持原位更新，必须明确标注，不能让“更新”按钮悄悄安装成另一份程序。

### 离线完整包（按需提供）

面向没有 WebView2 或无法下载运行环境的设备。安装版可以随包提供离线运行环境安装器；真正免安装的完整便携包需评估固定版运行环境及启动路径配置。代价是包体增大，以及固定运行环境的补丁维护责任。离线启动不代表无需连接语音/聊天服务器。

不建议为普通用户同时展示过多包型。下载页先突出安装版和便携版，离线完整包放在高级下载中。

## 更新交互与实现边界

建议状态：空闲 → 检查 → 可更新 → 下载 → 校验 → 已准备 → 等待合适时机 → 安装 → 新版启动确认。每一阶段有独立失败出口。

- 手动检查失败应可见；后台检查失败轻量记录，避免反复打扰。
- 默认通话/共享期间推迟后台下载，或由用户允许下载；后续确有需求再实现限速，避免占用游戏带宽。
- “结束通话后更新”需要用户选择，不擅自根据离开频道就退出应用。
- 安装前保存设置、草稿并完成有序断开；重新启动后恢复浏览位置，不自动重新开启麦克风或屏幕共享。
- 下载与安装拆分可以利用现有插件 API；跨客户端重启保留下载结果、断点续传、后台限速需要额外设计，不能视为拆分 API 后自动获得。
- 持久缓存使用稳定版本标识；读取缓存后重新校验，安装前再次验证可信产物。暂停后续检查对进行中任务的覆盖。
- 单实例锁避免两个更新器同时运行；失败时保留当前可运行版本。
- “客户端代码回滚”与“用户数据回滚”分开处理；数据迁移应保持兼容或有备份，启动失败恢复不能只切换 exe。

## Phase 与验收

| 阶段 | 交付内容 | 验收门槛 |
| --- | --- | --- |
| Update Phase 0：修齐发布基础 | 对齐产物格式、统一版本解析、手动检查、错误日志；明确旧版本迁移 | 全新安装、上一版升级、跨多版升级均在干净机器跑通，设置不丢失 |
| Update Phase 1：无打扰自动更新 | 下载/安装分离，准备完成状态，用户决定重启时机，统一状态机 | 通话中不自行退出；下载失败仍可使用旧版；错误签名被拒绝；新版成功启动 |
| Update Phase 2：便携分发 | ZIP、数据目录约定、依赖检测、原目录更新机制 | 解压能运行；非管理员可更新可写目录；中文路径、只读目录、多实例与中断均有合理结果 |
| Update Phase 3：发行可靠性 | stable/beta、独立更新源与局域网镜像、自动发布验证、撤回与恢复策略 | stable 不收到 beta；暂停坏版本分发；已经升级用户能获得更高版本修复；服务器不可达可诊断 |
| Update Phase 4：差分验证与上线 | 用连续真实版本比较全量/差分；选定引擎并保留全量兜底 | 测量下载大小、合成耗时、峰值内存、磁盘空间、成功率；跨版本、损坏基础包、中断可恢复 |

Phase 0–1 优先于差分方案。Phase 2 的底层选型若倾向迁移更新框架，应提前做小范围概念验证，避免先自研便携更新器又整体替换。

对外承诺使用验收结果，不承诺尚未测试的“完全静默”“无管理员权限适配所有旧安装”“任意系统无需依赖”。

## 差分更新路线

### A. 继续 Tauri 全量自动更新（近期推荐）

保持现有发布、签名和服务端接口，完善用户体验。当前接入是完整安装产物更新；不能把差分 ZIP 改个 URL 交给现有安装逻辑。若包体与下载时间已经较小，长期采用全量也合理。

### B. 评估 Velopack（中期候选）

Velopack 提供 Rust 接入和按文件生成二进制差分的机制，并在多个差分与完整包之间作成本选择。适合在确有传输成本时做验证。

这是打包、安装生命周期、更新缓存、分发清单及旧安装迁移的系统性选型，不是直接替换一个函数。需单独验证 Tauri 启动入口、WebView2 依赖、签名策略、便携路径及从现有 NSIS 客户端的过渡；同一安装只能由一套更新器负责。

### C. 自研差分辅助程序（后置）

如有必须控制的特殊部署需求，可以评估 Zstandard/bsdiff 等补丁方案。必须校验基线版本和哈希，在临时目录还原完整新版，并用受信任签名认证最终产物后再切换；仅有哈希不等于发布者身份验证。基线错误或补丁不划算时下载全量包。需要承担文件锁、中断恢复、签名、磁盘空间及数据兼容等长期维护成本。

差分评测使用真实已签名发布产物，覆盖纯 UI 修改、Rust 修改、依赖升级；不要用单个文本文件实验推算正式包效果。初步决策指标可设为典型版本明显节省下载、端到端更新时间更短且成功率不低于全量，具体阈值由实测决定。

## 其他值得加入的方向

- 首次加入：邀请链接或可复制服务器入口，自动填入连接信息，减少手输 IP；这是“开箱即用”的一部分。
- 更新与业务服务分离：官方可信源负责版本身份，局域网服务器可镜像相同签名产物。明确回退条件；HTTP 204 代表无更新，不能假设 Tauri 自动尝试下一源。
- 服务端与客户端协议兼容：声明最低兼容客户端版本，优先保留兼容窗口；确需升级时解释原因。
- 更新撤回：撤回清单只阻止后续安装，已经升级的客户端通常需更高版本修复包；不能把 latest 指向旧版本就当成完成回滚。
- 资源更新：可先独立更新声明式主题、表情等资源。可执行 UI/JS 热更新涉及原生接口兼容、签名和恢复，应后置，运行中的语音/共享期间不热替换逻辑。
- 发布自动化：保留 GitHub 构建归档及局域网分发，产物验证完成后再切换清单；发布成功应包含从客户端网络实际可下载的验证。
